## Authoring rules your own sessions will follow

You are building something whose output is instructions: a method, a plugin, a port. Every rule added competes with the rules already there.

### The slip list

**A slip in the tool's behaviour is one line appended to `slips.md`: the date, what happened, which document governs it.** It is not work. One occurrence is indistinguishable from the model's base error rate; a second against the same document is the first evidence of a pattern.

**A document with two or more lines against it gets one piece of work naming them.** A rule enters your own rule text only through that work. A bug in a script or hook is ordinary work.

### Wording

**State each rule bare, as the action required.** Main clause first, conditions after; short connectives (but, except that, unless, so long as); one idea per provision; every exception at the same level as the rule it qualifies. A prohibition is a signal that the action required was never specified. Reasons go to the record that decided the rule, not into the rule.

### Host and target

**Host** is your method as installed and running. **Target** is the editable source. A target change reaches the host only when it is packaged and installed again.

**Say which one you mean.** "The rules" and "the hooks" each name both. Discussion is about the target unless said otherwise.

**Verify a change by driving the new code directly.** Performing the guarded action for real exercises the installed host, the old code, so the guard never fires.

**A decided-but-unshipped rule is in force from the moment it is decided.** Your sessions read your queue and records, not only the installed copy.
